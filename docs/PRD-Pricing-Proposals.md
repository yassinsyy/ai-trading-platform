# PRD – MVP «Предложения цен»

## Цель
Доставить безопасную и аудируемую петлю ценообразования, которая даёт измеримый прирост валовой прибыли у продавцов WB/Ozon за 8–12 недель.

## Метрики успеха
- Основная: добавленная валовая прибыль vs контрольная когорта (+8–15% целевой диапазон) на покрытых SKU
- Вторичные: покрытие SKU предложениями (>40% к 6-й неделе), успешность публикаций (>99%), время утверждения предложения (<24 ч)
- Контр‑метрики: жалобы, возвраты, стоки, вызванные изменением цен

## Объём (In)
- Инжест данных (заказы, цены/скидки, остатки, промо, цены конкурентов)
- Базовый прогноз спроса (Darts или Prophet)
- Сервис предложений цен с защитами (пол маржи, лимит дельты, лимит частоты)
- Процесс утверждения/публикации и полный аудит
- Дашборд измерения эффекта (uplift)

## Вне объёма (Out)
- Продвинутая эластичность/каузальный анализ (фаза 2)
- Автоматические закупки (фаза 2)
- Кросс‑маркетплейс арбитраж (фаза 2)

## Пользователи и сценарии
- Менеджер по ценам: «Вижу предложения, сравниваю с текущей ценой, утверждаю/отклоняю, применяю пакетно»
- Руководитель операций: «Вижу аудит и здоровье публикаций; быстро замораживаю/откатываю»
- Владелец: «Смотрю недельный отчёт по эффекту и ROI по когортам и SKU»

## Потоки
1) Инжест → Прогноз → Предложение → Утверждение → Публикация → Измерение → Итерация
2) Инцидент: Обнаружить аномалию → Автозаморозка/алёрт → Откат → Причины → Фикс

## Контракты API (драфт)
- ml-service
  - POST /v1/forecast: { skuId, series[], horizon } → { forecast[] }
  - POST /v1/price/proposal: { skuId, forecast[], constraints } → { proposedPrice, rationale }
- core-api
  - POST /v1/pricing/proposals: создать батч из вывода ml
  - POST /v1/pricing/proposals/:id/approve | /publish | /reject
  - GET /v1/pricing/audit?skuId=…

## Модель данных (core-api, драфт)
- Sku(id, mp, identifiers, brand, cost, minMargin)
- PriceRule(id, scope, minMargin, maxDelta, maxFreq, stopList)
- PriceProposal(id, skuId, proposedPrice, source, status, createdBy, metadata)
- PriceChange(id, skuId, oldPrice, newPrice, publishedAt, jobId, result)
- AuditLog(id, actor, action, entity, diff, timestamp)

## Нефункциональные требования
- SLO: успешность публикаций >99%, p95 задержка < 3 c; API предложений p95 < 500 мс (кэш), очереди очищаются < 2 мин
- Безопасность: RBAC, хранение секретов, аудит; rate‑limit на уровне MP
- Наблюдаемость: структурные логи, метрики, алёрты на сбои/дрифт

## Риски и меры
- Лимиты/баны API → rate‑limit, backoff, shadow‑режим
- Проблемы качества данных → валидация, fail‑closed, алёрты
- Дрифт модели → мониторинг, safe mode (заморозка), еженедельная перекалибровка

## Вехи
- Неделя 2: инжест + базовый прогноз
- Недели 3–4: предложения + защиты + экран FE для утверждения
- Неделя 5: публикация + аудит + расчёт эффекта
- Недели 6–8: стабилизация, рост покрытия, первый кейс
